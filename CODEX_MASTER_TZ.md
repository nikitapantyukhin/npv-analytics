# 3. Технологический стек и архитектура

### Целевые технологии

- Frontend: **React + TypeScript + Vite**; React Router, Tailwind CSS, shadcn/ui или совместимые компоненты, React Query/TanStack Query, **Apache ECharts** для сложных графиков (включая waterfall), TanStack Table для реестров.
- Backend: **Python 3.12+ + FastAPI + Pydantic v2**, SQLAlchemy 2.x, Alembic; Python Decimal и date/time для финансовых вычислений.
- Database: **PostgreSQL**.
- Очередь: **Redis + RQ** (или совместимый простой task worker с долговременным хранением состояния в PostgreSQL).
- Внешний денежный движок: **Rust CLI `cfgen`**, собранный из зафиксированной ревизии nosnitches.
- Внешние кривые: **HTTP API QuantumTeam**, при необходимости через локально поднятый сервис по его официальному Docker-конфигу; не переписывать его код.
- Запуск: **Docker Compose**, одна документация по запуску в Windows 11 + WSL2 Ubuntu 24.04 и обычном Linux.
- Тесты: pytest, Vitest/React Testing Library, Playwright, интеграционные smoke/e2e.

Допускается технически эквивалентная библиотека, если она не мешает воспроизвести эталон и не создаёт лишних зависимостей. Не усложнять MVP микросервисами, Kubernetes, отдельной auth-платформой или LLM.

# 4. Разделы продукта: полные требования

## 4.1. ОБЗОР `/overview` (или `/`)

- Постоянная боковая навигация: «Обзор», «Генератор сделок», «Портфель», «Факторный анализ», «Кривые ставок», «Данные и интеграции».
- Верхняя панель: бренд NPV Analytics, выбор активного портфеля, дата оценки, статусы интеграций, доступные действия.
- KPI на реальных данных: суммарная NPV только если рассчитана; количество сделок; кредитная и депозитная компоненты; средневзвешенные показатели по корректно определённой базе; дата/статус последнего факторного анализа.
- Графики: динамика NPV только если есть достаточная серия дат; если истории нет — осмысленное пустое состояние, а не искусственная линия. Структура портфеля (кредиты/депозиты, fixed/float и т. д.).
- Блок последнего факторного анализа: базовая NPV, сценарная NPV, ΔNPV, тип изменения, ссылка на расчёт. При отсутствии расчётов — призыв создать портфель и выполнить анализ.
- Блок возможностей со статусами, основанными на реальном capability registry, а не макетных данных.
- Кнопки «Создать портфель», «Рассчитать», «Открыть последний анализ» должны вести к соответствующим операциям.

## 4.2. ГЕНЕРАТОР `/generator`

**Обязательно два режима с единым состоянием настроек:**

- «Простой»: название портфеля, кредитный/депозитный/смешанный тип, количество сделок, дата оценки, типовой пресет, seed (в дополнительных настройках); быстрые базовые диапазоны.
- «Расширенный»: общие настройки; суммы и сроки; типы графиков; ставки; досрочки; субсидии; экспертные параметры; статистический предпросмотр и распределения.
- Переключение между режимами не теряет значения.

**Генерация:**

- Кредиты, депозиты и смешанные портфели; для смешанного — контролируемая доля каждого типа, отдельные параметры для двух классов при необходимости.
- Суммы и сроки: минимумы/максимумы; распределение равномерное, нормальное, логнормальное, ручные интервалы с весами. Параметры распределений валидируются. Сроки — допустимые целые значения в месяцах.
- Категориальные доли: ANN/RGM/SIMPLE, FIXED/FLOAT, доли досрочек/субсидий; суммы процентов = 100%. Для известного количества сделок соблюдать точные количества по категориям через детерминированное распределение целых чисел (largest-remainder или эквивалент), фиксировать правила округления.
- Seed делает генерацию повторяемой при идентичной конфигурации и версии генератора.
- Даты выдачи/погашения, дата оценки, правило начисления процентов, день платежа, периодичность; допускать только комбинации, корректные для конкретного движка.
- Для FLOAT: индикатор, маржа, график пересмотра, cap/floor, лаг; ставки на форме в процентах, внутри адаптера — доли. Не смешивать маржу и итоговую ставку.
- Досрочное погашение: доля сделок, число событий, даты, суммы (абсолютные или доли остатка), проверка горизонта и знаков.
- Субсидии: доля, тип субсидийной ставки, маржа/индекс, календарь выплат; только при подтверждённой поддержке движком. Иначе интерфейс есть, действия явно ограничены.
- Для SIMPLE — только корректное формирование явного графика или погашения в конце срока; не выдавать `SIMPLE` без необходимых полей.
- Для депозитов обеспечить знак остатка и потока по контракту. В интерфейсе суммы показывать по модулю с явной маркировкой типа; оригинальный знак сохранять в расчётной модели.
- Валидация параметров на фронте и **обязательная повторная валидация на сервере**.
- Перед генерацией: «Проверить настройки», «Предпросмотр» (маленькая отдельная выборка с явной маркировкой), «Сгенерировать»; после: результаты, сравнение заданных и фактических долей, гистограммы, реестр, ошибки, сохранение, экспорт.
- При импорте/генерации нельзя молча пропускать ошибочные строки. Частичный результат маркировать.
- Предусмотреть шаблоны, сохранение настроек, воспроизведение по seed; шаблон не должен меняться после применения к конкретному портфелю без создания новой версии.
- Генерацию тысяч/десятков тысяч сделок выполнять на сервере в задаче; пагинация на сервере.

**Контракт генератора:** выходная сделка должна быть сериализуема в совместимый `deals.csv` для `cfgen`; не копировать чужой тестовый генератор вслепую и не генерировать набор абстрактных полей, которые не подходят движку.

## 4.3. ПОРТФЕЛЬ `/portfolios`, `/portfolios/:portfolioId`, `/portfolios/:portfolioId/deals/:dealId`

- Выбор сохранённого портфеля и версии, дата оценки, статус; карточки KPI (количество, кредитная компонента, депозитная компонента, NPV при наличии, ошибки).
- Четыре внутренние вкладки: **«Сделки»**, **«Денежные потоки»**, **«Структура»**, **«История расчётов»**.
- Реестр: ID, тип, остаток, начальная сумма, даты, FIXED/FLOAT, ставка, ANN/RGM/SIMPLE, NPV и статус; поиск, серверные фильтры, сортировка, пагинация, настройка колонок, CSV экспорт.

- История запусков: не перезаписывать старые результаты; показывать версию портфеля, дату оценки, версии движков/кривых.
- Изменение сделки после расчёта — **новая версия или сценарий**, никогда тихая правка исходного объекта.

## 4.4. ФАКТОРНЫЙ АНАЛИЗ `/analysis`

**Два режима обязательно представлены в интерфейсе:**

1. **«Сценарный анализ»**: изменение одного или нескольких факторов для сделки, выбранных сделок или целого портфеля; исходные параметры неизменяемы; сценарий отдельно сохраняется.
2. **«Изменение между датами»**: выбор начальной и конечной даты, снимков состава и кривых, сравнительные таблицы и графики; когда нет необходимых снимков или методики, вывести эталонное состояние «нет данных / ожидает интеграции» без выдуманного эффекта.

**Факторы:** договорная процентная ставка, сумма/остаток, срок, параметры досрочки и субсидии, кривая дисконтирования, прогноз индикатора плавающей ставки, дополнительные продуктовые параметры — только если можно построить валидную сценарную сделку. Отдельные действия не должны автоматически влиять на несвязанные параметры: повышение ключевой ставки не изменяет фиксированный договорный процент само по себе.

**Действия:** выбрать портфель/сделку, добавить фактор, задать дельту и единицы (%, п.п., б.п., месяцы, ₽), применить, сбросить, рассчитать, сохранить, открыть историю, экспортировать.

**Результат сценария:** исходная NPV, сценарная NPV, `ΔNPV` в ₽ и %, waterfall (с началом, вкладом каждого фактора и концом), сравнение исходных и сценарных потоков, таблица PV/DF, вклад сделок, диагностические предупреждения.

**Метод атрибуции:** последовательная подстановка с фиксированным **отображаемым порядком факторов**:

```
V0 = NPV(base)
V1 = NPV(apply(base, F1))
V2 = NPV(apply(base, F1, F2))
...
contribution_i = Vi - V(i-1)
ΔNPV = Vn - V0 = sum(contribution_i)
```

Фиксировать набор и порядок факторов; тестировать телескопическую сумму; возможную зависимость вкладов от порядка явно разъяснять. **Нельзя** вычислять независимые влияния факторов от базы и просто складывать их без учета взаимодействий. При изменении только DF **не запускать Rust заново**, использовать те же денежные потоки. При изменении условий сделки, влияющих на CF, выполнить реальный новый расчёт `cfgen`.

**Исторический режим:** не имитировать фактическую историю. Если нет снимков портфеля на обе даты, двух кривых или правил разложения эффекта времени, открыть экран и показать перечень недостающих данных. Сценарий изменения текущего портфеля **нельзя выдавать за исторический факт**. Когда есть реальные источники — реализовать вычисление и отчет с фиксацией дат, состава портфеля, выбытия/новых сделок и полученных платежей.

## 4.5. КРИВЫЕ СТАВОК `/curves`

**Четыре вкладки:** «Кривые», «Сценарии», «Дисконтирование и NPV», «История кривых».

- «Кривые»: выбрать дату, источник, снимок, базовую/сценарную кривую; интерактивный график по срокам, таблица ставок, сдвиги в б.п., экспорт, даты и версии.

# 7. Финансовая методика PV / NPV — реализация с явными допущениями

**Приоритет — проверяемость, сохранение знаков и сопоставимость с Excel спринта 2.** Методика предварительно утверждена владельцем проекта, но отдельные конвенции пока не подтверждены проверяющим: это нужно зафиксировать в `docs/FINANCIAL_METHODOLOGY.md` и показывать рядом с результатами.

## 7.1. Конвенция денежных потоков

- Берём `B_j = current_principal_amt` **со знаком**: кредит положительный, депозит отрицательный.
- Берём будущие платёжные события `CF_{j,i}` из `cashflow.csv` **со знаком**; нулевые `repricing/sub_repricing` не влияют на PV, но сохраняются.
- Не добавлять повторно начальную выдачу, если мы уже вычитаем остаток позиции на дату оценки. Не вычитать остаток дважды.
- Проводить раздельную сумму PV по потоку `client` и `sub`, затем суммировать в соответствии с подтверждённой методикой. Для неизвестного экономического смысла субсидии не скрывать допущение.
- Потоки в дату оценки по текущему контракту отсутствуют: `payment_dttm > report_dttm`; это должно совпадать с нашей формулой.

## 7.2. Формулы

Для сделки j:

```
PV_j = Σ_i [ CF_(j,i) × DF(valuation_date, payment_date_i) ]
NPV_j = PV_j - B_j
NPV_portfolio = Σ_j NPV_j
ΔNPV = NPV_scenario - NPV_base
```

Здесь `B_j` и `CF` со знаком по контракту. Для кредита это привычное из Excel **PV будущих платежей − текущий остаток долга**; для депозита — обобщение по знакам.

**Это условная согласованная экономическая оценка, а не автоматически бухгалтерская прибыль.** В отчёте отображать версию методики и явно учитывать начисленные проценты/субсидии как часть потока от внешнего движка. Если будет изменена методика экспертом, сделать новую версию `valuation_method`, а не тихо переписать исторические результаты.

## 7.3. Контрольный пример из прошлого Excel

Второй спринт, кредит:

```
B = 3 646 037.89 RUB
PV = 2 056 999.50 RUB
NPV = -1 589 038.39 RUB
```

**Условие сверки:** этот результат должен получиться **при тех же потоках, датах и DF**, которые были в Excel. Не требовать его от произвольного нового денежного графика и не подгонять расчёты. Написать unit-test на формулу и отдельный regression-test при наличии точного набора старых CF/DF.

## 7.4. Дисконт-факторы

Движок QuantumTeam возвращает ставки по срокам; термин `rate` ещё нуждается в семантической проверке. Реализовать **явно настраиваемую, версионируемую `DiscountConvention`**. Для ставки zero rate с непрерывным начислением возможна **учебная модель**:

```
t = ACT/365 (days from valuation date / 365)
DF(t) = exp(-r(t) * t)
PV_i = CF_i * DF(t_i)
```

Однако **использовать её для рабочих финансовых расчётов как default разрешено только при явном обозначении этого допущения**. Если исходная ставка не zero rate, не называть такой расчёт «подтверждённым методом QuantumTeam». Из договора о ставках должны следовать day-count, тип начисления, интерполяция и экстраполяция.

Для непрерывного параллельного сдвига можно проверить:

```
DF_scenario(t) = DF_base(t) * exp(-delta_rate_decimal * t)
```

Эта формула применима при принятой непрерывной конвенции и является **экспериментальной моделью**, как в Excel спринта 2; она не заменяет фактические сценарные кривые сервиса. Для неравномерного сдвига заново вычислять DF согласно принятой методике.

Для срока между узлами использовать документированную интерполяцию (например, по логарифму положительных DF или иной согласованный вариант). За пределами покрытия кривой не выполнять скрытую экстраполяцию: либо явное правило с маркировкой, либо ошибка «Срок вне диапазона кривой».

**Ключевая ставка и DF — разные сущности.** Не приписывать изменение ключевой ставки фиксированным договорам без реального правила. Если используется демонстрационный коэффициент передачи из Excel, он должен быть явным параметром сценария «экспериментальная модель», а не рыночным фактом.

## 7.5. Денежная точность и суммы

- Деньги представлять `Decimal`, округление применять на оговорённых границах; не использовать float для сложения рублёвых CF.
- Для экспоненты/DF использовать выбранную численную реализацию с документированной точностью, затем переводить результат PV в Decimal или устойчиво аккумулировать; финансовая сумма отображается до 2 знаков по согласованному правилу.
- При отсутствии валидного DF хотя бы для одного денежного события не считать NPV портфеля полным результатом.
- Для отчётов показывать unrounded internal PV и округлённое итоговое отображение по явно определённым правилам; отсутствие округлённых расхождений важно для waterfall.
- Процентное изменение `ΔNPV / |NPV_base| ×100%` допустимо при ненулевой базе; при базе 0 показывать «не определяется», а не бесконечность. Указать используемый знаменатель в UI.

# 8. Внутренняя модель данных, версии, история

Сущности как минимум:

- `Portfolio` — id, name, type (credit/deposit/mixed), created_at.
- `PortfolioVersion` — id, portfolio_id, version_no, valuation_date, immutable_config_hash, generation_seed, generator_version, created_at.
- `Deal` — id, portfolio_version_id, business_deal_id, kind, raw_input_contract_fields, normalized_fields, validation_status.
- `GeneratorConfiguration` — versioned JSON с точными настройками и алгоритмами распределения.
- `MarketDataSnapshot` — id, source, external_id, trade_date, retrieval_date, curve_type, scenario, unit/convention, raw JSON/hash, source SHA.
- `CurvePoint` — tenor, rate, shifted_rate и дополнительные подтверждённые поля.
- `KeyRateObservation` — indicator, effective_date, value, source.
- `CalculationRun` — id, type, portfolio_version_id, valuation_date, status, stage, started_at, finished_at, error_summary, engine_sha, market_snapshot_id, method_version, args_hash.
- `CashflowEvent` — привязка run/deal/event_order, дата, тип, stream, signed amount, before/after, rate, raw fields.
- `DiscountedCashflow` — run/event id, time_fraction, DF, PV, curve id, interpolation flags.
- `Scenario` — base run, factors, order, raw settings, resulting run, created_at.
- `FactorContribution` — scenario, step_index, factor, NPV_before, NPV_after, delta.
- `ValidationIssue`, `IntegrationHealthCheck`, `AuditEvent`, `StoredArtifact`.

Жёсткое правило: **никаких переписываний исторических финансовых результатов**. Новая генерация или новый расчёт создаёт новую версию. Сценарий ссылается на конкретные версии портфеля, кривой и денежного движка.

Сырые `deals.csv`, `cashflow.csv`, `errors.csv`, кривые и настройки сохранять с хешами и метаданными, чтобы было возможно воспроизвести отдельный расчёт.

Крупные портфели: batch insertion, индексы, серверная пагинация, стриминговый экспорт, bounded memory. Не отправлять в браузер 100 000 строк одним JSON.

# 10. Тесты и критерии приёмки

## 10.1. Финансовые тесты

- Нулевой сценарий: `ΔNPV = 0` в оговорённой точности.
- Изменение только discount curve меняет DF/PV, но **не** исходные CF и не вызывает повторный `cfgen`.
- Изменение договорной ставки или графика, влияющего на платежи, приводит к отдельному запуску `cfgen`; результат не копируется из базы как будто пересчитан.
- Сумма `NPV_j` согласуется с NPV портфеля (до округления).
- По правильно заданным знакам кредита и депозита совпадает ручная формула.
- Waterfall: сумма промежуточных вкладов равна итоговому `ΔNPV` в исходной точности.
- Неиспользуемый фактор не меняет результат; фиксированный кредит не репрайсится только от изменения CBKEY1M.
- При отсутствующих CF или DF система не выдаёт полную NPV.
- Контроль по нашему Excel выполняется на идентичном наборе DF/CF и фиксирует расхождения по методике.

## 10.2. Тесты генератора

- 1, 10, 1000 сделок; при возможности нагрузочный тест 10 000+.
- Тот же seed и версия алгоритма дают те же данные и тот же hash канонизированного результата.
- Типы credit/deposit/mixed, exact weights, корректные суммы категорий 100%, допустимые срок/даты/ставки.
- Сложные сочетания поддерживаются только при валидном контракте; иначе корректная диагностика.
- Нет повторных deal_id внутри версии; неверные значения не проходят в движок.
- Импорт и генерация используют один и тот же валидатор.

## 10.3. Интеграционные тесты

- Запустить Rust `cfgen` на официальных тестовых сделках; разобрать реальные `cashflow.csv` и `errors.csv`.
- Сверка с `testdata/golden` по суммам и остаткам; ориентир 0.01 ₽, подтверждённый контрактом.
- QuantumTeam health + реальный запрос кривой; при недоступности — честный offline-state. Не обозначать учебный набор как успешную интеграцию.
- Ошибочный CSV, пропавший сервис, timeout, пустой ответ, неизвестная единица ставки, отсутствие DF на платёж, частичный CF: проверяемое неуспешное состояние с диагностикой.
- Не подменять живые ошибки искусственными сообщениями.

## 10.4. UI/e2e тесты

- Работают все шесть основных маршрутов и все 15 утверждённых экранов.
- Переключение simple/advanced не сбрасывает данные.
- Генерация → портфель → карточка → платежи → PV/NPV → сценарий → waterfall.
- Выбор сохранённого снимка и повторное открытие сохранённого анализа воспроизводит отображаемый результат.
- Нерабочие функции показывают причину, доступные функции не заблокированы из-за стороннего модуля.
- Скриншоты Playwright 1600×1000 визуально сопоставлены с 15 PNG эталона.

## 10.5. Минимальный законченный сценарий защиты

1. Запустить проект по README.
2. Открыть «Обзор» без фиктивных KPI.
3. В генераторе создать воспроизводимый смешанный портфель (например 1000 сделок), увидеть фактические распределения.
4. Открыть портфель, выбрать сделку.
5. Запустить реальный `cfgen` по валидной подвыборке/портфелю; получить CF, остатки и ошибки.
6. Получить реальный snapshot QuantumTeam через API либо выбрать подтверждённый ранее полученный snapshot с подписью offline; если недоступен — показать учебный эталон отдельно с честным названием.
7. Посчитать NPV по явной, сохранённой финансовой конвенции.
8. Изменить договорную ставку или дисконтирование; получить новый результат, ΔNPV и waterfall.
9. Показать «Данные и интеграции»: SHA, источник, состояние, файлы и журнал.
10. Открыть исторический анализ и, если необходимых снимков нет, показать спроектированное объяснение ограничений и будущего шага.

**Важно:** если полноценный смешанный 1000-сделочный расчёт не проходит из-за ограничений внешнего движка, уменьшить *демонстрационную вычислительную выборку*, явно сообщить, какие сделки реально рассчитаны, сохранить полную генерацию и диагностику; никогда не показывать частичную NPV как NPV всех 1000 сделок.
